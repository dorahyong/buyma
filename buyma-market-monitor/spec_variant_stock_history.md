## 0. 요약

> 현재 `market_item_variants`는 **매 크롤마다 덮어써서** 재고 변화 이력이 전혀 남지 않습니다.
> **변형별 재고 상태가 바뀔 때만 1행을 남기는 이력 테이블** 하나를 신설해 주십시오.
> 기존 크롤러의 다른 동작은 **변경하지 않습니다.**

## 1. 요청 범위

### 해주실 것
1. `market_variant_history` 테이블 신설 (§4)
2. 상세크롤 시 변형 재고 상태가 **직전과 달라진 경우에만** 이력 1행 INSERT (§5)

### 건드리지 않는 것
- `market_items`, `market_stats_history`, `market_price_history`, `market_orders` 등 **기존 테이블 스키마·적재 로직 일체**
- 크롤링 주기, 재방문 스케줄러, 파싱 대상 페이지
- `market_item_variants`의 기존 UPSERT 동작 (그대로 유지)

변형 파싱은 **이미 하고 있으므로** 새로 긁을 페이지는 없습니다. 파싱 결과를 비교해 이력 행을 추가로 쓰는 것이 전부입니다.

### 1.1 실행 위치 — 기존 items 상세크롤러 내부 (중요)

**이 작업은 별도 크롤러도, 별도 배치도 아닙니다.**

> **기존 items 상세크롤러가 상품 상세페이지를 조회하는 바로 그 시점에, 그 프로세스 안에서 함께 처리합니다.**

| 항목 | 내용 |
|---|---|
| **실행 주체** | 기존 items 상세크롤러 (신규 크롤러 없음) |
| **실행 시점** | 상세페이지를 파싱해 `market_item_variants`를 UPSERT하는 **바로 그 지점** |
| **추가 네트워크 요청** | **없음** — 이미 파싱 중인 변형 데이터를 재사용 |
| **주기** | 기존 재방문 스케줄러(`market_revisit_state`)를 **그대로 따름**. 변형 이력용 별도 주기 없음 |
| **관측 시각** | 해당 크롤이 `market_stats_history`에 기록하는 **`observed_at`과 동일한 값** 사용 (§6 주의 ① 참조) |

즉 처리 순서는 다음과 같습니다.

```
기존 items 상세크롤러가 상품 1건을 조회
  → 상세페이지 파싱 (찜/조회/문의 + 변형 목록 + 가격 …)   ← 기존 동작
  → market_stats_history INSERT                          ← 기존 동작
  → [신규] 변형 상태를 직전과 비교해 달라진 것만 이력 INSERT
  → market_item_variants UPSERT                          ← 기존 동작
```

### 1.2 이 구조에서 따라오는 제약 (사전 공유)

이력의 해상도는 **재방문 스케줄러의 주기에 그대로 종속**됩니다. 현재 티어 분포는 다음과 같습니다.

| 티어 | 상품수 | 평균 관측 횟수 | 변형 이력 축적 |
|---|---|---|---|
| HOT | 58,013 | 9.98 | 잘 쌓임 |
| WARM | 159,688 | 3.44 | 보통 |
| **COLD** | **1,560,714** | **1.00** | **사실상 안 쌓임** |

**COLD 156만 개(전체의 88%)는 관측이 1회뿐이라 이력이 생기지 않습니다.** 이건 이번 요청으로 해결되는 문제가 아니라 **재방문 처리량의 문제**이며, 별건으로 다룹니다. 이번 스펙은 **재방문이 일어나는 상품(HOT+WARM 약 21.8만 개)에 대해 이력이 남도록 하는 것**이 목표입니다.

## 2. 배경 — 왜 필요한가

`InStock → OutOfStock` 전환은 **"방금 누가 샀다"의 근사**입니다.

현재 판매 데이터는 `market_orders`(추적 셀러 541명, 28.6만 행)뿐이지만, 변형 재고 이력이 생기면 **상품 181만 개 전체**에서 수요 신호를 얻습니다.

또한 **부분 품절은 완전 품절보다 앞서는 선행지표**입니다. 지금 이 순간 부분 품절 상태인 상품이 **35.5만 개(21%)** 있지만, **언제 그렇게 됐는지를 몰라서 쓸 수 없습니다.**

## 4. 기록 방식 결정 — **변화 시에만 기록(delta)**

두 방식을 검토해 **delta 방식으로 결정**했습니다. 근거는 아래와 같습니다.

### 4.1 두 방식 비교

기준: 현재 상세크롤 **하루 87,529 상품** × 변형 4.74개 = **하루 414,887 변형 판독**

| 방식 | 하루 행수 | 연간 용량 | 자기완결성 |
|---|---|---|---|
| **A. 전량 스냅샷** (판독할 때마다 전 변형 기록) | 414,887 | **~18.2 GB** | 있음 |
| **B. 변화분만 (채택)** | 20,000~41,000 | **~0.9~1.8 GB** | §4.3으로 확보 |

**10~20배 차이**입니다.

> 변화율 추정 근거: 완전 품절(`SOLD_OUT`) 전환이 하루 2,427상품 = 관측 상품의 2.8%. 부분 변화를 포함해도 변형 단위로는 5~10% 수준으로 추정.

### 4.2 delta를 택한 이유

**① 값이 안 바뀐 행은 정보량이 0입니다.**
어떤 사이즈가 5일 내내 `InStock`이었다면, 그 사실을 5번 기록하든 1번 기록하든 **알 수 있는 것은 동일**합니다. 스냅샷 방식은 하루 41.5만 행 중 **90% 이상이 "직전과 같음"의 반복**입니다.

**② 스냅샷의 유일한 장점은 이미 다른 곳에서 확보됩니다.**
스냅샷이 나은 유일한 지점은 *"기록이 없는 구간이 '안 봤다'인지 '봤는데 안 변했다'인지"* 를 자체적으로 구분하는 것입니다. 그런데 이건 **기존 `market_stats_history`로 판정됩니다** — §4.3 참조.

**③ 우리가 필요로 하는 신호는 전부 "전환 시점"입니다.**
"이 사이즈가 언제 빠졌나", "며칠 만에 한 색상이 통째로 소진됐나" 는 전부 변화 이벤트입니다. 무변화 구간은 앞뒤 전환 기록 사이의 간격으로 자동 도출됩니다.

### 4.3 "봤는데 안 변했다"를 판정하는 근거 (실측 확인 완료)

변형과 찜/조회는 **같은 상세크롤에서 함께 파싱**됩니다. 실측으로 확인했습니다.

| 확인 | 결과 |
|---|---|
| 변형 보유 상품 수 | **1,812,181** |
| `market_stats_history` 관측이력 보유 상품 수 | **1,812,182** |
| 표본 20,000개 교차 확인 | **20,000개 전부 양쪽에 존재 (100%)** |
| `market_stats_history` 기록 방식 | HOT 티어 실제 행수 **10.12** = 스케줄러 `obs_count` **10.12** → **매 관측 append 확정** |

따라서:

> **`market_stats_history`에 시각 T의 행이 있다 = 그 시점에 해당 상품의 상세페이지를 파싱했다 = 변형 재고도 그때 읽었다.**

이력에 기록이 없으면 **"안 본 것"이 아니라 "봤는데 안 변한 것"** 으로 확정할 수 있습니다. 조인만 하면 되므로 **크롤러를 변경할 필요가 없습니다.**

> ⚠️ **전제**: 이 설계는 `market_stats_history`가 **매 관측마다 append** 하는 현재 동작에 의존합니다. 향후 이를 "변화 시에만 기록"으로 바꿀 계획이 있다면 **미리 알려주십시오** — 그 경우 별도의 경량 관측 원장이 필요해집니다.

## 5. 스키마

```sql
CREATE TABLE market_variant_history (
  item_id      VARCHAR(64)  NOT NULL,
  variant_sku  VARCHAR(128) NOT NULL,
  observed_at  DATETIME     NOT NULL,
  availability TINYINT      NOT NULL COMMENT '0=OutOfStock, 1=InStock, 2=변형삭제',
  PRIMARY KEY (item_id, variant_sku, observed_at),
  INDEX idx_mvh_observed (observed_at)
) ENGINE=InnoDB;
```

### 컬럼 설계 근거

| 결정 | 이유 |
|---|---|
| `color`·`size` 미포함 | `market_item_variants`에 이미 있고, 카디널리티 2만/8천의 자유 텍스트 |
| `price` 미포함 | 표본 20만 상품 전부 전 변형 동일가 + `market_price_history`와 중복 |
| `availability`를 TINYINT | `varchar(32)`의 `'InStock'`/`'OutOfStock'` 대비 행당 ~10 B 절감 |
| `observed_at`을 DATETIME | varchar(32) ISO 문자열 대비 행당 ~20 B 절감, 날짜 연산도 직접 가능 |

> `observed_at`을 기존 이력 테이블들과 맞춰 `VARCHAR(32)` ISO8601로 하셔도 무방합니다. 그 경우 용량이 약 30% 늘어납니다(연 0.9~1.8 GB → 1.2~2.3 GB).

> ⚠️ **`idx_mvh_observed`는 반드시 생성 시점에 함께 만들어 주십시오.** `market_price_history`·`market_stats_history`에서 이 인덱스가 없어 시계열 집계가 풀스캔 → 원격 연결 한계(4~5분) 초과로 실패하던 문제를 이미 겪었고, 사후에 별도 요청드린 바 있습니다.

## 6. 적재 로직

**기존 items 상세크롤러가 상품을 조회하는 그 시점에**(§1.1), 파싱한 변형 목록을 **현재 상태 테이블과 비교**해 달라진 것만 기록합니다.

```
# 기존 items 상세크롤러가 상품 1건의 상세페이지를 파싱한 직후 지점

observed_at = 이번 크롤의 관측 시각        # market_stats_history에 쓰는 값과 동일한 변수
parsed      = 이번에 파싱한 변형들          {variant_sku: availability}
current     = SELECT variant_sku, availability
              FROM market_item_variants WHERE item_id = ?

BEGIN TRANSACTION

  INSERT market_stats_history (...)              # 기존 동작 그대로

  for sku, avail in parsed:
      if sku not in current:                     # 신규 변형 등장
          INSERT market_variant_history (item_id, sku, observed_at, avail)
      elif current[sku] != avail:                # 상태 변화 (양방향 모두)
          INSERT market_variant_history (item_id, sku, observed_at, avail)
      # 무변화 → 아무것도 기록하지 않음

  for sku in current:
      if sku not in parsed:                      # 변형이 사라짐
          INSERT market_variant_history (item_id, sku, observed_at, 2)

  UPSERT market_item_variants                    # 기존 동작 그대로

COMMIT
```

### 주의 4가지

**① `observed_at`은 같은 크롤이 `market_stats_history`에 쓰는 값과 동일해야 합니다.**
호출 시점마다 `NOW()`를 새로 부르지 마시고, **크롤 시작 시 한 번 정한 관측 시각 변수를 두 테이블에 함께 넘겨** 주십시오.

이게 어긋나면 §4.3의 판정 논리가 깨집니다. 우리는 *"`market_stats_history`에 시각 T 행이 있다 → 그때 변형도 봤다"* 로 무변화를 판정하는데, 두 테이블의 시각이 몇 초씩 어긋나면 그 대응이 흐려집니다. **정확히 같은 값이면 조인 한 번으로 끝납니다.**

**② 이력 INSERT와 현재상태 UPSERT를 같은 트랜잭션으로 묶어 주십시오.**
이력만 실패하고 현재 상태가 갱신되면 그 전환은 **영구히 유실**됩니다. delta 방식의 유일한 취약점이므로 트랜잭션으로 막아야 합니다.

**③ `OutOfStock → InStock` 복원도 반드시 기록해야 합니다.**
재입고가 남지 않으면 "아직 품절"과 "돌아왔다"를 구분할 수 없어 소진 속도가 왜곡됩니다.

**④ 최초 1회는 전 변형을 기록해도 됩니다.**
테이블 생성 직후 첫 크롤에서는 비교 대상이 없으므로 현재 상태를 그대로 넣어 기준선을 만들어 주십시오. 843만 행 × ~120 B ≈ **1 GB 일회성**입니다. (생략하고 이후 변화분부터 쌓아도 무방하나, 기준선이 있으면 분석 시작이 빨라집니다.)

## 8. 확인이 필요한 사항

### ① `variant_sku`의 시간적 안정성 — 가장 중요

상품 수정이나 재출품 시 `variant_sku`가 **유지되는지** 확인이 필요합니다. 값이 바뀌면 매번 "기존 변형 삭제 + 신규 변형 등장"으로 잘못 기록되어 이력이 무의미해집니다.

표본 50만 행이 **100% `item_id` 접두** 구조라 BUYMA 고유 ID를 그대로 쓰는 것으로 보이며 긍정적이지만, **실제 검증이 필요합니다.**

### ② `(item_id, color, size)` 5.5% 중복의 정체

표본 50만 행에서 472,721 조합만 나왔습니다. 같은 상품에 동일한 색상·사이즈가 두 행 이상 존재합니다. 실제로 별개 변형인지, 파싱 중복인지 확인 부탁드립니다.

### ③ `stock_min` / `stock_max` 수집 가능성

현재 843만 행 **전부 NULL**입니다. BUYMA가 `残り◯点` 같은 잔여 수량을 노출하는 경우가 있는지, 파싱 가능한지 확인 부탁드립니다. 가능하다면 소진 속도를 훨씬 정밀하게 측정할 수 있습니다. **(이번 요청의 필수 항목은 아닙니다.)**

## 9. 적용 후 검증

```sql
-- 1) 양방향 전환이 모두 기록되는지 (0·1·2가 전부 나와야 정상)
SELECT availability, COUNT(*) FROM market_variant_history GROUP BY availability;

-- 2) 인덱스 사용 확인
EXPLAIN SELECT COUNT(*) FROM market_variant_history WHERE observed_at >= '2026-08-10';

-- 3) 현재 상태 테이블과 최신 이력의 정합성 (불일치가 없어야 정상)
SELECT COUNT(*) 불일치
FROM market_item_variants v
JOIN (
  SELECT h.item_id, h.variant_sku, h.availability,
         ROW_NUMBER() OVER (PARTITION BY h.item_id, h.variant_sku ORDER BY h.observed_at DESC) rn
  FROM market_variant_history h
) x ON x.item_id = v.item_id AND x.variant_sku = v.variant_sku AND x.rn = 1
WHERE x.availability <> (v.availability = 'InStock');

-- 4) 일별 적재량 추이 (용량 추정이 맞는지)
SELECT DATE(observed_at) 날짜, COUNT(*) 행수
FROM market_variant_history GROUP BY 날짜 ORDER BY 날짜;
```
