# 기획서 — `market_exposure_history` (품번 노출순위 시계열 수집)

작성 2026-07-28 · 요청 대상: buyma market monitor 크롤러 개발 · 근거: rank_strategy_v1.md

---

## 1. 배경 / 목적

동일 품번(brand_model_number) 경쟁에서 **검색결과 노출순위가 매출의 지배 요인**임을 데이터로 확인했다:
- 노출 **top3가 그 품번 주문의 89%**를 독식(노출 1위 주문 중앙값 8건 vs 나머지 0건).
- 노출순위는 가격·출품시기(외생 레버) + 조회·찜(플라이휠)로 형성되며, 노출↔조회는 8.5배 자기강화.

그런데 **현재 market DB는 노출순위를 어디에도 저장하지 않는다.** `market_stats_history`(찜·조회·문의), `market_price_history`, `market_orders`는 시계열로 쌓이지만, **검색결과 순위(노출)는 수집 대상이 아님**. 지금까지의 노출 데이터는 전부 수작업 스냅샷(파일)이라 지속 추적·인과분석(예: Δ찜 선행 → Δ노출 후행)이 불가능하다.

**목적**: 추적 품번의 노출순위를 주기적으로 수집·적재해, 찜·조회처럼 **노출도 시계열화**한다. 이로써 (a) 경쟁 포지션 상시 모니터링, (b) 노출↔판매·찜·조회의 **시차 인과분석**, (c) 자사/경쟁 리스팅의 노출 변동 추적이 가능해진다.

## 1.5. 기존 크롤러 수집 구조와의 통합 (중요)

크롤러 일 총 예산 ≈ **300,000 조회/일**. 수집 항목의 **우선순위(예산 배분 순서)**는 다음과 같이 고정한다:

| 순위 | 수집 항목 | 방식 | 일 소요 |
|---|---|---|---|
| 1 | 셀러 정보 | **매일 전량(고정)** | (소량) |
| 2 | 셀러 orders 정보 | **매일 전량(고정)** | (소량) |
| **3 (신규)** | **품번별 노출순위 스냅샷** | **매일 전량 스윕(고정)** — 경쟁(2+셀러) 품번 전수 1회 | **≈ 54,000 (§8)** |
| 4 | 셀러 items 정보(찜·조회) | **위 1·2·3을 제하고 남는 예산을 분배** — 활발한(찜·조회 축적·주문 유입) 상품 위주 | 잔여 전부 |

→ **노출 스냅샷은 items와 예산을 다투는 소비자가 아니라, 셀러·orders와 같은 "매일 전량 수집" 고정 의무로 둔다.** 노출 전량 스윕을 먼저 확보한 뒤, **items가 남는 예산을 기존 가치기반 방식으로 분배**한다.

- 노출은 **경쟁 품번 전수를 매일 1회**씩 도므로 품번별 적응형 주기(자주/드물게)가 **불필요** — 그냥 매일 전량.
- 부수효과: 노출을 전량 매일 확보하면 **모든 경쟁 품번의 촘촘한 노출 시계열**이 쌓여, Δ찜/Δ조회 → Δ노출 **시차 인과분석**이 상시 가능해진다.

## 2. 범위

### 2-1. 수집 대상 품번 — **경쟁(2+셀러) 품번으로 확정**
- 소스: `market_items.brand_model_number`(비어있지 않은 값).
- **대상 = 서로 다른 셀러 2곳 이상이 같은 품번을 파는 "경쟁 품번" 그룹.**
  - 단일 셀러·단일 상품 품번은 **제외** — 항상 1위/1개라 노출추적이 무의미하고 크롤 부하만 키움.
  - 자사가 취급/취급예정인 품번은 경쟁 셀러 수 무관하게 **포함**(자사 대시보드용).
- **규모(실측 2026-07-28)**: 전체 active distinct 품번 **489,095** 중 단일셀러가 **434,978(89%)** → 제외. **경쟁(2+셀러) 품번 = 54,117**이 수집 대상. (참고: 3+셀러 17,274 / 4+셀러 7,854)
- 대상 산출 쿼리(배치): `brand_model_number`로 GROUP BY 하여 `COUNT(DISTINCT seller_id) >= 2`인 품번 집합. (대형 GROUP BY이므로 야간 배치·인덱스 활용 권장. 대상 목록은 일 1회 갱신.)

### 2-2. 페이지 범위 — **1페이지만 수집 (권장)**
검색결과 첫 페이지(추천순 `-O1` 기본 정렬)만 수집한다. **뒷페이지는 수집하지 않는다.**

근거:
1. **매출의 89%가 top3, 사실상 top 페이지에서 발생.** 1페이지 밖 리스팅은 경쟁적으로 무의미(죽은 노출)이므로, "1페이지 진입 여부 + 진입 시 순위"만으로 필요한 신호가 다 잡힌다.
2. **활발한(값이 쌓이는) 상품일수록 상위 노출** → 자주 수집되는 고가치 상품은 결국 대부분 1페이지 안에 있어, 1페이지만으로 충분한 커버리지 확보.
3. **노출 로직은 페이지 구간별로 다르지 않다**(전역 추천순 하나) → 1페이지가 알고리즘의 top 판단을 그대로 담는다.
4. **부하**: 품번당 1요청 vs 전 페이지네이션(품번당 수~수십 요청). 수만 품번 규모에서 1페이지만이 유일하게 현실적.

트레이드오프(수용): 자사 리스팅이 1페이지 밖이면 "몇 위인지"까지는 모르고 "top 페이지 밖"이라는 사실만 안다. → v1에선 충분. (필요 시 §9의 "심층 프로브" 선택 확장)

## 3. 데이터 모델

### 3-1. 신규 테이블 `market_exposure_history` (리스팅 단위, append-only)
| 컬럼 | 타입 | 설명 |
|---|---|---|
| `snapshot_id` | bigint | 스냅샷 배치 식별자(같은 수집 실행·같은 품번 묶음) |
| `model_query` | varchar(255) | 실제 검색에 쓴 품번 쿼리 문자열(정규화 후) |
| `rank` | int | 1페이지 내 노출 순위(위=1) |
| `item_id` | varchar(64) | 리스팅 상품 id (market_items와 조인 키) |
| `price_yen` | int | 검색결과에 표시된 가격(엔) |
| `seller_name` | varchar(255) | 표시 셀러명 |
| `seller_id` | varchar(64) NULL | 해석 가능 시 market_sellers.seller_id |
| `observed_at` | datetime | 수집 시각 |

- PK: (`snapshot_id`, `rank`) 또는 (`model_query`,`observed_at`,`rank`). 인덱스: `item_id`, `model_query`, `observed_at`.

### 3-2. 스냅샷 요약 테이블 `market_exposure_snapshot` (품번×시각 단위)
| 컬럼 | 설명 |
|---|---|
| `snapshot_id` | PK |
| `model_query` | 품번 쿼리 |
| `observed_at` | 수집 시각 |
| `n_results_page1` | 1페이지 리스팅 수 |
| `total_results` | 검색이 보고한 전체 결과 수(있으면) |
| `floor_price_yen` | 1페이지 최저가 |
| `status` | ok / blocked / empty / error |

→ 요약 테이블로 "이 품번을 언제 수집했나/최저가 추이"를 가볍게 조회, 상세는 history로.

## 4. 수집 동작

1. 대상 품번 큐에서 `model_query` 하나를 꺼낸다.
2. URL 구성: `https://www.buyma.com/r/-O1/<URL인코딩(model_query)>/`
   - 공백 → `%20`. 정렬 코드 `-O1`(추천순=현재 노출 로직) 고정.
3. 첫 페이지 HTML 요청(기존 상세 크롤러의 HTTP 인프라·헤더·재시도 재사용).
4. 결과 리스트를 **표시 순서 그대로** 파싱: 각 항목의 `item_id`(상품 링크 `buyma.com/item/NUMBER/`에서), `price_yen`, `seller_name`, 순위(표시 위치). 전체 결과 수 표기가 있으면 함께.
5. `market_exposure_history`에 리스팅 append + `market_exposure_snapshot`에 요약 1행.
6. 차단/빈결과/에러는 status로 기록(빈 행이라도 남겨 "그 시각 수집됨"을 보존).

**주의**: 가격 오름차순 등으로 재정렬 금지 — **화면 표시 순서(=노출순위)를 반드시 보존**.

## 5. 품번 정규화 (쿼리 생성)

`brand_model_number`는 표기가 제각각(하이픈·공백·다색 코드 나열). 검색 일관성을 위해:
- 다색 상품은 대표 코드 하나로(또는 원문 그대로) — 원문 그대로가 무난(BUYMA 검색이 다코드 문자열도 처리).
- 앞뒤 공백 trim, 내부 공백은 `%20` 인코딩.
- 같은 물건이 표기만 다른 경우(`DD1391-100` vs `DD1391 100`)는 v1에선 별건으로 두되, 향후 정규화 키로 병합 고려(§9).

## 6. 매칭 / 활용

- `market_exposure_history.item_id` ↔ `market_items.item_id`로 조인 → 노출 리스팅에 우리가 아는 속성(가격·찜·조회·이미지·태그·셀러) 결합.
- `observed_at`로 `market_stats_history`와 시각 정렬 → **Δ노출 ~ Δ찜/Δ조회 시차분석** 가능(핵심 목적).
- 자사 상품 item_id로 필터 → "우리 리스팅이 각 품번에서 몇 위인지" 상시 대시보드.

## 7. 스케줄링 — 매일 전량 스윕 (고정 의무, 적응형 아님)

**노출 수집은 셀러·orders와 동일한 "매일 전량 수집" 고정 항목이다.** 품번별 적응형 주기는 두지 않는다.

- **동작**: 매일 1회, 경쟁(2+셀러) 품번 **전수(≈54k)**를 `-O1` 1페이지로 스윕.
- **대상 목록 갱신**: 일 1회 배치로 `COUNT(DISTINCT seller_id)>=2` 품번 집합 재산출(신규 경쟁 품번 자동 편입, 경쟁 소멸 품번 자동 제외).
- **예산 관계**: 노출 스윕(≈54k)은 셀러·orders와 함께 **먼저 확정 차감**되고, **items(④)가 그 잔여 예산을 기존 가치기반 방식으로 분배**한다. → 노출은 items와 경쟁하지 않고, items가 노출을 제한 나머지를 쓴다.
- **상태 관리(경량)**: `market_exposure_state(model_query, last_collected_at, last_status)` 정도로 "오늘 수집했는지"만 추적하면 충분(적응형 점수·주기 불필요). 하루 안에 실패한 품번은 당일 잔여 시간/예산 내 재시도.

## 8. 성능 · 부하 · 예산 (실측 기준)

**일 예산 300,000 조회 대비 노출 스윕 소요:**
| 항목 | 값 |
|---|--:|
| 수집 대상(경쟁 2+셀러 품번) | 54,117 |
| 1일 전량 스윕 = 필요 조회 | **≈ 54,117 / 일** |
| **일 예산 대비 노출 몫** | **≈ 18%** |
| items(④)에 남는 예산 | 300,000 − (셀러+orders+54,117) ≈ **약 82% 내외** |

- 매일 전 경쟁품번을 다 훑어도 **18%**면 되고, 나머지 대부분이 items 수집에 남는다.
- 대상 수는 셀러·상품 증가에 따라 완만히 늘지만, 경쟁이 소수 품번에 집중돼(전체의 11%) 폭증하지 않음 → 예산 여유 충분.
- **레이트리밋·차단 회피**: 동시성 상한, 요청 간 지연, 재시도/백오프, 실패 status 기록. 기존 크롤러 매너 준수.
- **저장량**: 리스팅 ~40개 × 54k 품번 × 매일 ≈ 일 200만 행 규모 → 파티셔닝/보존정책(예 raw는 N개월 후 요약만 유지) 필요.

## 9. 엣지케이스 · 한계 · 선택 확장

- **1페이지 밖 자사 리스팅**: 순위 미상(→ "top 페이지 밖" 플래그만). 필요 시 **선택적 심층 프로브**: 자사 취급 품번 한정으로 자사 item_id 나올 때까지 최대 N페이지 추적(비용 큼, 옵션).
- **검색 노이즈**: 키워드 매칭이라 유사·타상품 소량 혼입 가능 → item_id 조인으로 자사/경쟁 정품만 선별 분석.
- **품번 표기 분산**: 정규화 병합은 v2 과제.
- **정렬 코드**: `-O1`(추천순=노출) 고정. 향후 다른 정렬 비교는 별도.

## 10. 이 데이터로 가능해지는 분석 (가치)

1. **노출 시계열** — 찜·조회처럼 노출도 시간축으로.
2. **시차 인과** — Δ찜/Δ조회(선행) → Δ노출(후행) 검증(현재 불가, 이 테이블로 가능).
3. **자사 노출 대시보드** — 품번별 우리 순위·최저가 갭 상시.
4. **경쟁 이동 감지** — 특정 셀러의 노출 급등/급락 알림.

---

## 11. 단계별 구현 제안

- **MVP**: 경쟁(2+셀러) 품번 대상, 1페이지 수집, 두 테이블 적재, 고정 주기(예 3일). — 이것만으로 시차분석·대시보드 즉시 가능.
- **v2**: 적응형 스케줄러(§7), 품번 정규화 병합, 자사 품번 심층 프로브(옵션).
