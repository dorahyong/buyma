## ★ 모든 이야기의 전제 — 바이마에 올라간 상품은 ②를 다시 안 만듭니다

`okmall/raw_to_ace_converter.py:780` · `kasina/raw_to_converter_kasina.py:1085`

변환(CONVERT)은 **아직 바이마에 안 올라간 상품만** 처리합니다. 주석에도 "등록된 건 stock 전담"이라고 적혀 있습니다.

그런데 옵션 목록을 통째로 새로 만드는 건 **변환밖에 없습니다**
(`raw_to_ace_converter.py:1157` / `raw_to_converter_kasina.py:1483` — `DELETE FROM ace_product_variants` 후 다시 INSERT).
재고동기화는 이미 있는 줄의 재고 표시만 고칩니다 (`update_ace_variants_stock` = `UPDATE ... SET stock_type`).

> **결론: 바이마에 올라간 순간부터, 그 상품의 옵션 목록(②)은 영원히 그때 그대로입니다.**
> 사이즈가 늘지도 줄지도 않고, 재고 표시만 바뀝니다.

여기서 지금 문제 대부분이 나옵니다.
참고로 ①(몰 원본)은 수집기가 `ON DUPLICATE KEY UPDATE` 로 매일 갱신하고 있어서,
**최신 옵션 목록은 이미 DB에 들어와 있는데 아무도 안 쓰고 있는 상태**입니다.

### ③④는 ②를 베낄 뿐 — 몰에 다시 접속하지 않습니다

재고동기화가 도는 순서:

```
재고동기화가 몰 접속 → 새 옵션 목록 받음
   ↓ 이 중 "DB에 있는 줄과 매칭된 것"만 써서
② ace_product_variants 의 stock_type 만 UPDATE
   ↓ _reconcile_published() 호출
reconcile → ensure_group
   ↓ _scoped_indexes_for_options 가 ② 를 읽음        ★ 여기가 핵심
③ source_offering_options 씀  (load_options)
   ↓
④ listing_options 재적재  (resolve)
   ↓
BUYMA edit push
```

- `okmall/reconcile_runner.py` 에 `requests` / `playwright` / HTTP 호출 **0개**. reconcile 은 순수 DB→DB
- 재고동기화는 `raw_scraped_data` 에도 안 씀 (건드리는 건 상품 삭제할 때뿐)

> **몰에서 새로 받아온 옵션 목록은 매칭된 줄의 재고 상태만 뽑아 쓰고, 나머지는 메모리에서 그냥 버려집니다.**

→ **③④만 고쳐서는 실시간 데이터가 바이마로 못 갑니다.** ③에 실시간 데이터를 넣어주는 통로가 ②밖에 없기 때문입니다.
J(뒤에 나옴)만 고치면 **기존 냉동 9,423개는 풀리지만 앞으로 새로 생기는 D-1은 그대로**입니다.

## 1. 매칭이 실제로 어떻게 도는가

재고동기화가 상품 하나를 볼 때 두 목록을 비교합니다.

### DB 쪽 (`ace_product_variants`) — okmall 예시

| color_value | size_value | color_value_original | size_value_original | source_option_code | stock_type |
|---|---|---|---|---|---|
| ブラック | 270 | 블랙 | 270 | 5581234 | purchase_for_order |
| ブラック | 275 | 블랙 | 275 | 5581235 | purchase_for_order |

- `color_value` / `size_value` = **바이마 표시용(일본어)** — 매칭에 안 씀
- `~_original` = **몰에서 온 한글 원본** — 매칭 2순위
- `source_option_code` = 몰이 준 옵션 고유번호 — 매칭 1순위

(2026-05-21 개편. 그전엔 `color_value` 한 칸이 표시용과 매칭용을 겸했고,
번역이 그 칸을 덮어써서 매칭이 깨진 게 5,320건 사고의 원인이었음)

### 몰 쪽 (이번에 읽어온 것)

| 몰 | 어디서 뽑나 | 옵션 고유번호 |
|---|---|---|
| okmall | 상세페이지 옵션표 `tr[name="selectOption"]` 의 `sinfo` 속성 | `sinfo` 의 마지막 토막 |
| 네이버 21몰 (t1global 포함) | 상품 JSON `optionCombinations` | 그 조합의 `id` (`str(c.get('id', i))`) |
| cafe24 몰들 | HTML 옵션 태그 | 몰에 따라 있기도/없기도 |

```python
{'color': '블랙', 'size': '270', 'option_code': '5581234', 'status': 'in_stock'}
```

수집기와 재고동기화가 같은 방식으로 번호를 만듭니다
(네이버: `premiumsneakers_collector.py:603` == `stock_price_synchronizer_naver_merge.py:777`).

### 비교 순서

`detect_stock_changes` — 13개 재고동기화 스크립트 전부 동일한 코드
(`okmall/stock_price_synchronizer_merge.py:904`, `naver/stock_price_synchronizer_naver_merge.py:891`, …)

1. DB 옵션의 고유번호가 몰 목록에 있으면 → 그 재고 상태를 씀
2. 없으면 → (한글 색상, 한글 사이즈)로 다시 찾음
3. 그것도 없으면 → **아무것도 안 하고 넘어감**

## 2. 케이스별 동작 — 정상 / 누락 / 잘못됨

### ✅ A. 고유번호 일치 — 정상

DB `5581234` ↔ 몰 `5581234`.
재고있음 ↔ 품절 양방향 다 반영됩니다. 이름이 일본어로 번역돼 있어도 상관없습니다.
가장 많은 케이스이고 잘 돕니다.

### ✅ B. DB에 고유번호가 없고, 한글 색·사이즈가 일치 — 정상

DB 고유번호가 비는 경우:
- cafe24 계열 일부 몰 (보유율 편차 큼 — nextzennpack 42%, euroline 52%)
- 사이즈표(measurements)에서 만들어낸 옵션 (`source_option_code: None`, 처음부터 out_of_stock)
- 단일옵션 fallback

`('블랙','270')` ↔ `('블랙','270')` 로 잡힙니다.
**다만 몰이 표기를 조금만 바꿔도 깨집니다.**

### ✅ C. 고유번호는 어긋났지만 이름이 같음 — 정상

판매자가 옵션을 지웠다가 같은 이름으로 다시 만들면 번호가 새로 발급됩니다.
이때 2순위(이름)로 구제됩니다. 의도된 동작입니다.

### 🔴 D. 번호도 이름도 못 찾음 → 그냥 넘어감 ← **문의 7·25**

`okmall/stock_price_synchronizer_merge.py:963` · `naver/stock_price_synchronizer_naver_merge.py:950`

```python
if mall_status is None:
    # 매칭 실패 → skip (보수적). 진짜 단종은 별도 명시 도구로 처리.
    continue
```

여기서 **완전히 성격이 다른 세 가지가 한 덩어리로 묶여 있습니다.**

| | 실제 상황 | 지금 동작 | 맞나 |
|---|---|---|---|
| D-1 | 판매자가 그 사이즈를 아예 내렸음 (삭제/미사용) | 넘어감 → **바이마엔 재고있음 그대로** | ❌ 없는 재고 판매 |
| D-2 | 몰이 표기를 바꿈 (`270`→`270mm`, `블랙`→`BLACK`) + 번호도 새로 발급 | 넘어감 | ❌ 옛 옵션 냉동 + 새 옵션도 안 들어옴 |
| D-3 | 수집이 부실해서 목록이 일부만 읽힘 | 넘어감 | ✅ 이건 넘어가는 게 맞음 |

**5,320건 사고 때문에 D-3을 지키려고 D-1·D-2까지 같이 봐주고 있는 상태**입니다.
지금 코드에는 이 셋을 가를 근거가 아예 없습니다.

주석의 "진짜 단종은 별도 명시 도구로 처리" — **그 도구는 아직 없습니다.**

**문의 7(okmall)과 25(t1global)가 바로 D-1입니다.**

### 🔴 E. 몰엔 있는데 DB엔 없음 (새 사이즈 입고) → **아무도 안 넣음**

비교가 **DB 옵션을 하나씩 돌면서**(`for variant in db_variants`) 이뤄집니다.
몰에만 있는 옵션은 쳐다보지도 않습니다.

그리고 위 ★ 때문에 등록된 상품은 변환을 안 타니,
**새로 들어온 사이즈는 영원히 바이마에 안 올라갑니다.**

냉동의 반대 방향 손실인데, **지금 아무도 안 세고 있습니다.** 규모 미상.

재고 판정이 뒤집힐 수 있습니다.

**매칭 키는 제대로 고쳤는데 `not_found` 분기는 고치지 않고 통째로 들어냈고,
그 자리에 대체 동작을 안 넣었습니다.** 그때부터 냉동 시작.
= 사고 대응의 미완성 부분 (당시 "작업 규모가 커서 미뤘다"고 한 그 자리).

### E(새 옵션) — 처음부터 없었습니다

최초 버전도 `for variant in db_variants:` — **DB에 있는 줄만 훑습니다.**
몰에만 있는 옵션은 최초 버전부터 지금까지 한 번도 본 적이 없습니다.
고도화로 누락된 게 아니라 **원래 설계가 "DB 목록은 고정, 상태만 켜고 끄기"**.

### J(merge 재료) — merge 고도화 때 새로 생겼습니다

`source_offering_options` 라는 중간 칸이 merge 때 새로 생겼는데 **삭제 로직 없이 만들어졌습니다.**
이것만 고도화 때 새로 생긴 문제.

| | 언제부터 | 원인 |
|---|---|---|
| D 사라진 옵션 냉동 | 2026-05-27 | 사고 대응 중 대체 동작 미구현 |
| E 새 옵션 누락 | 처음부터 | 설계 누락 |
| J merge 재료 냉동 | merge 고도화 | 새 칸 만들며 삭제 안 넣음 |

## 4. 그래서 문의 7·25는

둘 다 **D-1** 이고, 등록된 상품은 옵션 목록이 다시 안 만들어진다는 전제(★) 때문에
**한 번 얼면 영원히 안 풀립니다.** 담당자가 손으로 내리기 전까지는.

그리고 D-1을 고쳐도 **J를 같이 안 고치면 ③에 남아서 그대로 올라갑니다.**
두 개는 같이 가야 합니다.

## 6. 고칠 방향 — stock 이 옵션 목록을 다시 만들어야 합니다

재고동기화는 **이미 몰에 접속해서 완전히 새로운 데이터를 받아옵니다.**
그런데 그걸 "있는 줄 켜고 끄기"에만 쓰고 버립니다.
수집기와 똑같이 **옵션 목록 자체를 다시 만들면** ②가 진실이 되고 ③④는 자동으로 따라옵니다.

### ★ 범위를 나눕니다 — 지금 푸는 건 "없는 재고 판매"입니다

문의 7·25 = **D-1**(사라진 옵션 안 내림) + **J**(③ 안 지움).

**E(새 옵션 추가)는 다른 건입니다.** "팔 수 있는데 안 팔고 있다"는 매출 기회 얘기이고
클레임과 무관합니다. **묶으면 아래가 전부 딸려옵니다.**

| E를 묶으면 딸려오는 문제 | 상태 |
|---|---|
| 새 옵션이 **한글로 먼저 바이마에 올라감** (아래) | 확인됨 |
| 바이마 API 로 옵션 **추가**가 되는지 | 미확인 |
| 새 옵션의 사이즈 상세(치수)를 어디서 가져올지 | 미확인 |

**D 와 J 는 이 중 하나도 필요 없습니다.** 이미 있는 옵션을 내리는 것뿐이라
새 이름을 만들 일이 없고, 따라서 번역이 끼어들 자리가 없습니다.

→ **E 는 분리. 클레임 해결에 불필요하고 위험만 늘립니다.**

### 번역 순서 문제 (E 를 할 때 반드시 걸리는 것)

번역 배치는 **등록된 상품도 대상입니다** — `okmall/convert_to_japanese_gemini.py:255`
(`is_active=1` + 옵션에 한글이 남아있으면 대상. 등록 여부를 안 봄.
`--price-checked-only` 도 재고동기화가 `buyma_lowest_price_checked_at` 을 갱신해서 통과)

**하지만 stock 은 번역을 하지 않고, edit 을 즉시 보냅니다.**

```
stock 이 새 옵션(한글)을 ② 에 넣음
   ↓ 같은 실행 안에서 _reconcile_published() 바로 호출
③ → ④ → BUYMA edit push          ← 이때 한글 그대로 올라감
   ↓ (나중에, 별도 배치)
TRANSLATE 가 ② 를 일본어로 바꿈
   ↓ (그 다음 reconcile 이 돌아야)
BUYMA 에 일본어로 다시 edit
```

푸시가 보내는 값은 `listing_options.color_value / size_value`
(`reconcile_buyma_push.py:113`) — `ace_product_variants` 의 표시용 칸을 그대로 타고 온 것.
**그 순간 한글이면 한글이 바이마로 갑니다.**

→ E 를 하려면 "번역 전 옵션은 push 에서 제외" 같은 장치가 따로 필요합니다.

### 이미 갖춰져 있는 것

**파싱 코드가 수집기와 이미 같습니다**

- 네이버: 옵션 고유번호 만드는 줄이 글자 하나까지 동일
  (`premiumsneakers_collector.py:603` == `stock_price_synchronizer_naver_merge.py:777`)

→ **재료는 이미 똑같이 만들어 놓고 쓰는 방법만 다른 상태.**
