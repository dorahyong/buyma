# 케이스별 상세

전부 같은 예시로 설명합니다. **나이키 운동화, 250/260/270 세 사이즈**로 바이마에 올라가 있는 상품.

DB(②)에는 이렇게 들어 있습니다. — 테이블 `ace_product_variants`

| 색상(일본어) | 사이즈 | 색상(한글원본) | 사이즈(한글원본) | 옵션번호 | 재고 |
|---|---|---|---|---|---|
| `ace_product_variants`<br>`.color_value` | `ace_product_variants`<br>`.size_value` | `ace_product_variants`<br>`.color_value_original` | `ace_product_variants`<br>`.size_value_original` | `ace_product_variants`<br>`.source_option_code` | `ace_product_variants`<br>`.stock_type` |
| ブラック | 250 | 블랙 | 250 | 5581001 | 있음 |
| ブラック | 260 | 블랙 | 260 | 5581002 | 있음 |
| ブラック | 270 | 블랙 | 270 | 5581003 | 있음 |

각 칸의 역할:

| 컬럼 | 역할 | 매칭에 쓰나 |
|---|---|---|
| `color_value` / `size_value` | 바이마에 보낼 **표시용**(번역됨) | ❌ 안 씀 |
| `color_value_original` / `size_value_original` | 몰에서 온 **한글 원본** | ✅ 2순위 |
| `source_option_code` | 몰이 준 **옵션 고유번호** | ✅ 1순위 |
| `stock_type` | `purchase_for_order`(있음) / `out_of_stock`(품절) | 갱신 대상 |

> `재고` 칸의 "있음"은 실제로는 `stock_type='purchase_for_order'` 입니다.
> 사장님 방침상 재고가 있으면 전부 '주문 후 매입'으로 넣기 때문에 `stock_in_hand` 는 거의 안 씁니다.

## ✅ A. 옵션번호가 맞는 경우 — 정상

몰에서 읽어온 것:

```
{옵션번호 5581001, 블랙, 250, 품절}
{옵션번호 5581002, 블랙, 260, 재고있음}
{옵션번호 5581003, 블랙, 270, 재고있음}
```

번호로 하나씩 찾아 상태를 덮어씁니다. 250이 품절로 바뀌고, 바이마에서 250이 내려갑니다.

일본어 이름은 비교에 안 씁니다. 그래서 번역이 뭘 하든 안 깨집니다. **가장 많은 경우이고 잘 돕니다.**

---

## ✅ B. 옵션번호가 없고 이름으로 맞는 경우 — 정상

몰에 따라 옵션번호를 안 주는 곳이 있습니다(카페24 계열 일부). 그럼 DB의 옵션번호 칸이 비어 있습니다.

이때는 **한글 원본**끼리 비교합니다. `(블랙, 270)` ↔ `(블랙, 270)`.

동작은 하지만 **몰이 표기를 바꾸면 바로 깨집니다.** `270` → `270mm` 로만 바뀌어도 못 찾습니다.

---

## ✅ C. 번호는 바뀌었는데 이름은 그대로 — 정상

판매자가 270 옵션을 지웠다가 다시 만들면 몰이 새 번호를 줍니다.

```
DB:  5581003 / 블랙 / 270
몰:  7729110 / 블랙 / 270     ← 번호가 다름
```

1순위(번호)는 실패하지만 2순위(이름)로 잡힙니다. 의도된 구제 장치이고 잘 돕니다.

## 🔴 D. 번호도 이름도 못 찾는 경우 — **여기가 문의 7·25**

```python
if mall_status is None:
    continue        # 아무것도 안 하고 다음 옵션으로
```

**문제는 "못 찾는다"가 세 가지 전혀 다른 상황에서 똑같이 발생한다는 것입니다.**

### D-1. 판매자가 그 사이즈를 아예 내림 ← **실제 클레임**

몰에서 읽어온 것:

```
{5581001, 블랙, 250, 재고있음}
{5581002, 블랙, 260, 재고있음}
                              ← 270이 목록에서 사라짐
```

- 250, 260은 번호로 찾아서 상태 갱신 ✅
- **270은 못 찾음 → 그냥 넘어감**

결과: DB의 270은 **"재고있음" 그대로**입니다. 바이마에서 270이 계속 팔립니다. 주문이 들어오면 매입할 수가 없습니다.

#### ★ 못 고치는 이유는 "데이터가 없어서"가 아닙니다

**재고동기화는 270이 없다는 걸 이미 알고 있습니다.**
`stock_price_synchronizer_naver_merge.py --source t1global` 을 돌리면 그 상품 페이지에 다시 접속해
`optionCombinations` 전체를 새로 받아옵니다. 250·260만 있고 270은 없는 목록이 **그 순간 메모리에 그대로 있습니다.**

문제는 **받아온 목록을 안 쓴다**는 것입니다.

```python
# detect_stock_changes 가 만들어내는 것 = changes 리스트
{'variant_id': ..., 'new_status': ...}      # ← UPDATE 지시서뿐

# 그걸 받는 쪽
def update_ace_variants_stock(self, stock_changes):
    UPDATE ace_product_variants SET stock_type=%s WHERE id=%s     # ← UPDATE 문 하나
```

`db_variants`(DB 목록)와 `mall_options`(몰 최신 목록)를 둘 다 손에 쥐고 있어서
**"DB에 있는데 몰엔 없는 것"을 이미 알 수 있습니다.**
실제로 그 지점에 도달합니다 — `mall_status is None` 이 정확히 그 상태입니다.
거기서 `continue` 로 버립니다.

#### 다른 경로로 고쳐질 가능성도 없습니다

재고동기화가 못 고치면 누가 고쳐주느냐 — 아무도 안 고쳐줍니다 (위 구조 1·2·3).

- 변환이 다시 돌면 목록을 새로 만들어서 270이 사라질 텐데 → 등록된 상품은 변환을 안 탐
- 수집이 다시 돌면 최소한 원본이라도 갱신될 텐데 → 등록된 상품은 수집도 건너뜀

**담당자가 손으로 내리기 전까지 계속됩니다.**

#### 고치는 방향

`mall_status is None` 일 때 `continue` 대신 **품절로 내리면** 그 뒤는 이미 있는 배관을 타고 자동으로 흐릅니다.

```
② 270 을 out_of_stock 으로 표시
   ↓ _reconcile_published()  (이미 붙어 있음)
③ loader 가 ②를 베끼면서 ③의 270 도 out_of_stock
   ↓
④ resolve 가 out_of_stock 은 union 에서 제외 → 270 빠짐
   ↓
BUYMA edit → 270 내려감
```

**남은 장애물은 D-3 하나뿐입니다.** 봇 감지·파싱 실패로 목록이 반만 읽혔을 때도
똑같이 `mall_status is None` 이 되기 때문입니다.

#### ★ 지우지 말고 "품절 표시" 여야 합니다

②에서 행을 **삭제**하면 ③에 짝 잃은 행이 남습니다.
loader 가 ②를 훑으며 채우는 구조라, ②에 없는 행은 ③에서 손도 못 댑니다.
**그게 지금 J(냉동 2,770건)가 생긴 방식입니다.**

반대로 ②에 행을 **남겨두고 `out_of_stock` 으로 바꾸면**, loader 가 그 행을 ③에 덮어써서
③도 같이 품절이 됩니다. **J 를 새로 만들지 않습니다.**

### D-2. 몰이 표기를 바꿈

```
DB:  5581003 / 블랙 / 270
몰:  8834221 / BLACK / 270mm     ← 번호도 이름도 전부 다름
```

- 옛 270: 못 찾음 → 넘어감 → **재고있음으로 냉동**
- 새 270mm: DB에 없음 → 아무도 안 넣음 (아래 E)

**결과가 최악입니다.** 실제로는 같은 상품인데, 바이마엔 못 파는 270이 남아 있고 팔 수 있는 270mm는 안 올라갑니다.

### D-3. 수집이 부실했음 ← 이건 넘어가는 게 맞음

봇 감지로 페이지가 반만 렌더링되거나, 몰이 HTML을 바꿔 파싱이 일부만 되면:

```
몰에서 읽힌 것: {5581001, 블랙, 250, 재고있음}     ← 260, 270이 안 읽힘
```

260, 270을 "사라졌다"고 판단하면 **멀쩡한 재고를 내려버립니다.** 이게 5,320건 사고입니다.

### 세 가지를 가를 근거가 코드에 없습니다

D-1(진짜 사라짐)과 D-3(못 읽음)은 **재고동기화 입장에서 완전히 똑같이 보입니다.** 둘 다 "DB에 있는 옵션이 몰 목록에 없다"입니다.

지금은 셋을 전부 D-3으로 취급합니다. 그래서 안전하지만 D-1이 영구 냉동됩니다.

**주석에는 "진짜 단종은 별도 명시 도구로 처리"라고 적혀 있는데, 그 도구는 만들어지지 않았습니다.**

```python
if len(db_variants) == 1 and len(mall_options) == 1:
```

흔하진 않지만 걸러내는 장치가 없습니다.

## 🔴 I. 수집 자체가 실패했을 때 — okmall만 다릅니다

여기는 방향이 반대인 문제입니다.

**다른 12개 몰**은 이렇게 나눕니다.

```
"일시적 오류" (타임아웃, 로드 실패)  →  아무것도 안 함, 다음 회차로
404 / 판매 종료                      →  이 몰 옵션 전부 품절 표시
```

**okmall만 이 구분이 없습니다.** 403(차단)과 연속 타임아웃만 빼고, **나머지 모든 오류를 "수집처에서 상품이 없어졌다"로 봅니다.**

여기 걸리는 것들:

- `요청 타임아웃`
- `요청 오류: (네트워크 오류 전부)`
- `빈 응답`
- `파싱 오류: (HTML 구조 변경 등)`

이 중 하나만 나도 **그 상품 옵션 전부가 품절 처리**됩니다. 잠깐 네트워크가 튄 것뿐인데요.

바로 잡히긴 합니다 — 다음 회차에 정상 수집되면 되살아납니다. 하지만 그 사이 바이마에서는 출품정지로 내려갑니다.

**13개 재고동기화 스크립트 중 okmall 하나만 가드가 없습니다.**

# 그래서 지금 무엇이 문제인가

## 1. 실제 클레임(없는 재고 판매)의 주범은 D-1입니다

J를 재봤더니 라이브 675건뿐입니다. 문의가 두 건 들어올 규모의 유일한 원인으로 보기엔 작습니다.

**D-1은 아직 규모를 모릅니다.** 그리고 DB만으론 알 수가 없습니다 — 몰 원본(①)이 등록 상품에 대해 낡아서(72%가 31일+) 대조할 기준이 없기 때문입니다. **몰에 직접 접속해야 압니다.**

## 2. D-1을 고치려면 D-3과 구분해야 하는데, 그 신호가 없습니다

지금 코드는 "이번 수집이 온전했나"를 어디에도 기록하지 않습니다. 옵션 몇 개를 읽었는지, 파싱이 정상이었는지가 남지 않습니다.

**이 신호를 만드는 게 D-1 해결의 전제입니다.** 신호 없이 "매칭 실패 = 사라짐"으로 바꾸면 5,320건이 재발합니다.

## 3. 근본 원인은 stock이 collector와 다르게 동작하는 것입니다

stock은 이미 몰에 접속해서 완전한 새 목록을 받아옵니다. 그런데 그걸 **"DB에 있는 줄 켜고 끄기"에만 쓰고 나머지는 버립니다.**

collector처럼 **받아온 목록으로 옵션 목록을 다시 만들면** D-1과 E가 동시에 없어지고, ②가 진실이 되니 ③④는 자동으로 따라옵니다.
