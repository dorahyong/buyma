## 1. 무엇을 만드나

등록대기 상품마다 **일일예상판매수(건/일)** 를 산출한다. 이 값 하나가 모델의 전부다.

```
일일예상마진액 = 일일예상판매수 × margin × c        ← 이 줄은 소비하는 쪽(ERP)이 한다
                                                    c = 0.6107 (금액 환산 보정, §7.4)
```

마진은 ERP가 정해 놓은 확정값이라 추정할 것이 없다. 채점 근거는 **시장 수요**다(우리 90일 402건이 아니라 market 90일 104,480건). 우리 데이터가 쓰이는 곳은 포획률 κ 하나뿐이다.

## 2. 공식 — 전부다

```
일일예상판매수(i) = κ × D(i) × adj(i) ÷ 90

D(i)   = 그 상품이 매칭된 셀에서 시장이 90일에 리스팅당 몇 개 파는가 (§3)
adj(i) = 품번이 매칭됐을 때만, 그 품번의 시장 찜이 셀 평균 대비 몇 배인가 (§4.3) · 기본 1.0
κ      = 포획률 = 0.3663 (§5)
```

## 3. D — 시장 수요 밀도

### 3.1 셀 정의 (4단 사다리)

```
셀 밀도 = (셀의 최근 90일 market_orders 건수) / (셀의 market_items ACTIVE 리스팅 수)

L1  품번(mn_norm) × 브랜드            ← 매칭되면 최우선
    (매칭률: published 풀 53.4% — 리스팅 기준 / 대기풀 ~28.0% — 고유 품번 기준. 분모가 다르니 직접 비교 금지)
L3  브랜드 × 카테고리 × 가격밴드       ← L1 미매칭분 대부분
L4  카테고리 × 가격밴드
L6  전역 = 0.0565

계층 축소:  D_L4 = (ord90_L4 + k × 0.0565)  / (n_L4 + k)
            D_L3 = (ord90_L3 + k × D_L4)    / (n_L3 + k)
            D_L1 = (ord90_L1 + k × D_L3*)   / (n_L1 + k)      k = 50
            * L1의 상위층 = 그 상품 자신의 L3 밀도 (없으면 L4, 없으면 L6)
```

- 가격밴드(JPY): `<10k / 10–20k / 20–30k / 30–50k / 50–80k / 80–120k / 120k+`
- **분자·분모 모집단 규칙**: 분자(ord90)는 **status 불문** — `market_items`에 행이 존재하는 주문 전부를 센다(전역 96,925가 이 기준이다. 팔린 뒤 품절·삭제된 아이템의 주문을 빼면 잘 팔리는 셀일수록 과소집계된다). 분모(n_act)만 ACTIVE. ⚠️ `market_matching_features_v1.md` §7의 "ACTIVE의 주문" 문구는 오기이며 본 규칙이 정본이다.
- **L1 밀도는 사전집계할 수 없다** — 상위층이 상품마다 다르기 때문. 채점 시 품번 셀의 (분자, 분모)를 lookup해서 축소식을 그 자리에서 계산한다. 곱셈 몇 번이라 비용은 없다.
- 시장 품번 셀은 평균 1.1 리스팅이다. **표본 하한을 두지 말 것** — 축소가 소표본을 자동으로 상위층에 붙인다(주문 없는 품번 셀은 D_L3와 거의 같아지고, 주문이 있으면 위로 뜬다). 1차 백테스트에서 하한 30은 L1을 전멸시켰다(AUC 0.617).
- L5(밴드 단독)는 두지 않는다. L4 미만은 바로 전역이다(v1과 동일).

### 3.2 왜 이 네 축인가

| 축 | 근거 |
|---|---|
| **품번** | 매칭 구간 AUC 0.787→0.848. 시장의 같은 상품 실적이 가장 강한 신호 |
| **브랜드** | 빼면 AUC 0.665로 붕괴. 절대 유지 |
| **가격밴드** | 시장 주문밀도가 밴드 간 17.5배 단조 감소 |
| **카테고리** | 브랜드 없는 셀의 유일한 대안 |

분모 정규화(리스팅당 밀도)가 핵심인 것, 가격을 별도 승수로 곱지 않는 것(이중계산)은 v1과 같다.

## 4. L1 — 품번 매칭 (v1.1의 신규 요소 ①)

### 4.1 매칭 규칙

```
키    : 우리 buyma_listings.model_no  ↔  시장 market_items.brand_model_number
      : 양쪽 모두 mn_norm(정규화 품번)으로 변환 후 등가 비교
가드  : 브랜드 일치 필수 — UPPER(TRIM(SUBSTRING_INDEX(l.brand_name,'(',1))) = UPPER(TRIM(m.brand))
      : 품번 충돌이 실재한다 (`005FJ0000` = Levi's ∧ Nike) · TRIM은 양쪽 다 (§10-2)
```

### 4.2 mn_norm 정규화 — 선행 작업 (생략 불가)

`market_matching_features_v1.md` §3의 규칙 그대로. 요지:

```
올바른 순서:  TRIM → 공백으로 토큰 분리 → 토큰별 UPPER + 비영숫자 제거 → 길이 4 이상만 채택
              → 토큰 여러 개면 여러 행 적재 (item_id 1 : mn_norm N)
잘못된 순서:  문자열 전체에서 구분자 제거  ← 금지 (복수 코드가 한 칸에 든 행이 쓰레기 토큰이 된다)
배제        :  범용코드 블랙리스트 (FREE, 001, ONE SIZE 류)
```

- 정규화 효과 실측: 원문 매칭 22.4% → **28.0%** (대기풀 고유 품번 기준).
- 스키마·인덱스 요청은 `db_indexing_request_draft_matching.md`. 백필 1회 + 크롤 시 증분.

**1:N 토큰의 정본 저장소** (한 품번 필드에 복수 코드가 흔하다):

| 쪽 | 저장 | 규칙 |
|---|---|---|
| market | **`market_item_codes`** (`src='field'` 행) | 인덱싱 요청서 B-3 테이블을 그대로 쓴다. `market_items.mn_norm` 스칼라 컬럼은 대표 토큰 캐시일 뿐, **L1 집계의 소스가 아니다** |
| 우리 | 저장 안 함 | 채점 배치가 `model_no`를 §4.2 규칙으로 **실시간 토큰화**한다(5만 건 × 순수 함수라 비용 없음) |

집계·조회 유일화 기준: **(item_id, code_norm)** — 같은 코드가 `src='field'`와 `'desc'`로 중복 적재될 수 있으므로 src를 무시하고 유일화한 뒤 집계한다(§10-3).

### 4.3 adj — 품번 찜 상대비 (신규 요소 ②)

```
adj = clip( mn_max_fav / cell_avg_fav , 0.5 , 3.0 )

mn_max_fav   = 그 품번(mn_norm) × 같은 브랜드의 시장 아이템 중 최대 fav_count
cell_avg_fav = 그 상품의 L3 셀 평균 fav_count (없으면 L4, 그것도 없으면 adj=1.0)
               평균은 셀의 ACTIVE 리스팅 전체 기준 — 찜 0인 리스팅 포함
적용 조건     = L1 매칭 시에만. 미매칭이면 1.0
엣지         = cell_avg_fav가 0 또는 NULL이면 adj = 1.0 (0으로 나누기 금지 — 정보 없음으로 취급)
```

- **분자에도 브랜드 가드를 건다.** (2차 백테스트는 미가드 분자로 측정했고 캡 덕에 피해가 제한적임을 확인했지만, 운영은 가드가 맞다.)
- **실태를 알고 쓸 것**: 매칭 상품의 92%가 하한 0.5에 붙는다(품번 찜 0이 대부분). 즉 adj는 사실상 "품번에 시장 찜이 없다 → 절반 감점" + 상위 8%의 연속 보정이다. 그래도 AUC +0.017을 번다.
- 찜은 누적 스냅샷이라 나이 인플레이션이 있다 — 상대비 + 캡이 유일한 방어이며, velocity 전환은 시계열이 쌓인 뒤(v2 과제).

## 5. κ — 포획률 (우리 데이터를 쓰는 유일한 지점)

```
κ = (우리 최근 90일 실주문 건수) / Σ_published( D(i) × adj(i) × 노출일(i)/90 )

  노출일(i) = min(90, 게재 후 경과일)
```

- **적합값 = 0.3663** (2026-08-11, published 풀 74,660개 기준). ⚠️ v1의 0.3069을 그대로 쓰면 안 된다 — adj가 평균적으로 점수를 깎으므로(92%가 0.5) 같은 402건을 맞추려면 κ가 올라간다. **공식 구성이 바뀌면 κ는 반드시 재적합**이고, 주 1회 갱신은 v1과 같다.
- κ를 금액에 맞춰 낮추지 말 것(v1 §4의 경고 그대로). 금액 보정은 c의 몫이다.

## 6. 대상 집합 — v1과 동일

```sql
SELECT l.id, l.brand_name, l.category_id, l.price, l.model_no, o.margin_amount_krw
FROM buyma_listings l
JOIN source_offerings o ON o.id = l.winner_offering_id
WHERE l.is_published = 0
  AND l.is_active    = 1
  AND o.margin_amount_krw > 0

```
규모 50,906개. `is_margin_ok=0` 1,829개의 처리 등 주의사항은 v1 §5 그대로다. `model_no`는 후보 100% 보유.

## 7. 배치

**7.1 사전집계 (일 1회)** — 테이블 2개.

```sql
-- v1의 market_demand_cells에 avg_fav 컬럼만 추가
CREATE TABLE market_demand_cells (
  level    ENUM('L3','L4','L6'),
  cell_key VARCHAR(255),
  n_act    INT,
  ord90    INT,
  density  DECIMAL(12,8),          -- 축소 적용 후
  avg_fav  DECIMAL(14,4),          -- ★ 신규: 셀 ACTIVE 리스팅 평균 fav_count (adj 분모, 찜 0 포함 평균)
  refreshed_at DATETIME,
  PRIMARY KEY (level, cell_key)
) DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_uca1400_ai_ci;   -- market 쪽에 맞춘다 (§10-1)

-- ★ 신규: 품번 셀 (밀도는 여기 두지 않는다 — §3.1, 채점 시 계산)
CREATE TABLE market_mn_cells (
  mn_norm  VARCHAR(64),            -- 인덱싱 요청서의 mn_norm과 동일 길이
  brand_key VARCHAR(120),          -- := UPPER(TRIM(market_items.brand))
  n_act    INT,                    -- ACTIVE 리스팅 수 (분모)
  ord90    INT,                    -- 최근 90일 주문 (분자, status 불문 — §3.1)
  max_fav  INT,                    -- adj 분자
  refreshed_at DATETIME,
  PRIMARY KEY (mn_norm, brand_key)
) DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_uca1400_ai_ci;
```

- 집계 소스는 `market_item_codes`를 **(item_id, code_norm)으로 유일화한 집합**이다(§4.2). `n_act`·`ord90`·`max_fav` 전부 그 집합 기준.
- **`n_act=0`이어도 `ord90>0`이면 행을 만든다** — 전부 품절된 히트 품번이 정확히 L1이 필요한 경우다. 이때 `D_L1 = (ord90 + 50×D상위) / (0 + 50)`.
- 조회 키(우리 쪽): `UPPER(TRIM(SUBSTRING_INDEX(brand_name,'(',1)))`.

**7.2 채점 (일 1회)**

```
for 각 대상 상품 i:
  1) 키 생성        mn_norm(들), brand_key, cat_key, band
  2) 상위층 D 계산   market_demand_cells lookup (L3→L4→L6)          ← v1과 동일
  3) L1 시도        market_mn_cells lookup — 있으면 D_L1 = (ord90+50×D상위)/(n_act+50), adj 계산
                    (우리 토큰이 여러 개면 각각 조회해 하나만 쓴다. 선택 순서: n_act DESC →
                     ord90 DESC → mn_norm ASC — 동률 시에도 결정적이어야 전진 검증의 점수 동결이 성립한다.
                     정규화 결과 유효 토큰이 0개면 L1 미시도 = 미매칭, adj 1.0)
  4) 산출           expected_sales_daily = κ × D × adj ÷ 90
  5) 적재           score_index_draft
```

**7.3 출력 테이블** — v1 스키마에 두 컬럼 추가.

```sql
d_level  VARCHAR(2)      -- 'L1' 추가 (L1/L3/L4/L6)
d_adj    DECIMAL(6,4)    -- ★ 적용된 adj (미매칭 1.0)
```
`d_level='L1'` 행의 `d_cell_key`는 `'mn_norm|brand_key'`를 저장한다. `DECIMAL(12,8)` 정밀도 경고, `d_level` 필수 기록은 v1 §6.3 그대로.

### 7.4 금액 환산 — 소비하는 쪽의 몫

```
일일예상마진액 = expected_sales_daily × source_offerings.margin_amount_krw(현재값) × c

c = 0.6107        (2026-08-11 적합. κ와 함께 주 1회 재적합)
  = (published 풀의 실제 일일마진 합계 285,165원/일) / Σ_published( expected_sales_daily × margin )
```

- "실제 일일마진 합계"는 **Σ(주문마진 ÷ 노출일)** 기준(관례 A)으로 고정한다. published 운영 총액과 실측상 일치하지만(0.996배), published 명세 §6의 정의식(Σ마진÷90)과는 노출일<90 상품에서 미세하게 다르다. 이 관례를 바꾸면 c 값이 달라지니 주의.
- c는 총액만 맞춘다. 가격밴드별 오차는 v1.1에서도 남는다 — `120k+`에서 **2.66배 과대**이고, 이 밴드는 **v1(동일 관례 2.47배)보다 오히려 소폭 나빠졌다**(품번 매칭이 밴드 오차를 고치는 도구가 아니라는 뜻이다. κ의 마진 의존 문제는 별개 과제로 남는다). "이 후보 100개 올리면 얼마 버나"는 여전히 최대 ~2.7배 틀릴 수 있고, 마진은 조회 시점 계산(뷰) 원칙도 v1 §6.4 그대로다.

## 8. 슬롯 교체 규율 — v1 §8 그대로 (생략 불가)

보호 기간 90일 · 91일+만 하위 퇴출 · `score_demoted` 영구 제외 · 일일 상한 1,500건 · **풀 분리(A안)**: 출품중은 published 점수로, 대기중은 draft 점수로 각자 정렬해 교체. 출품중 상품에 draft 점수를 쓰지 않는다. 근거와 주의는 v1 §8 전문을 따른다.

## 10. 구현 주의 — v1 §9 전부 유효 + 추가 3건

1. **(v1 §9 그대로)** collation 경계·`CREATE TABLE...SELECT` collation 상속·브랜드 키 정규화·`category_path` 파싱·`sale_date` varchar·분자/분모 모집단 일치(전역 96,925 ÷ 1,714,804)·dev 청크 처리.
2. **시장 브랜드 후행 공백 실재** (`'ECCO '`). SQL 비교는 PAD SPACE collation이라 무시되지만, 앱 코드·로컬 조인에서는 반드시 TRIM. (2차 백테스트에서 실제로 걸렸다 — 55건 불일치.)
3. **mn_norm은 1:N**이다(한 아이템에 복수 코드). 집계 전에 `market_item_codes`를 **(item_id, code_norm)으로 유일화한 집합**을 만들고, `n_act`·`ord90`·`max_fav` 전부 그 집합에서 계산할 것. 같은 코드가 src별로 중복 적재될 수 있으므로 `DISTINCT item_id`를 리스팅 수에만 걸면 **주문 분자가 이중집계된다.** 아이템 하나가 서로 다른 코드의 여러 셀에 기여하는 것은 의도된 동작.
4. **k=50을 바꾸지 말 것.** k=10이 백테스트 AUC를 0.848까지 올리는 것이 실측됐지만, 같은 기간 데이터로 고른 값이라 과적합·시점 누수에 취약하다. **11월 전진 검증에서 k 그리드 {10, 25, 50}으로 판정한 뒤에만 변경한다.**

1. **대기풀에서는 이득이 희석된다.** 위 층 분포는 published 풀 기준이고, 대기풀의 품번 매칭률은 정규화 후 ~28%다. 미매칭 상품의 점수는 v1과 사실상 같으므로(순위 상관 0.954), v1.1의 개선은 매칭 구간에만 나타난다. **노출 크롤 시딩 확대 등 커버리지 작업이 이득의 크기를 직접 결정한다.**
2. **L1 동일창 누수 가능성.** 시장 품번 신호와 정답이 같은 90일 창이다. 검증에서 최악 가정 시 v1과 동률까지 축소될 수 있음을 확인했다(현실적 추정은 그보다 한참 아래 — 판매 매칭행의 59.5%가 자기포함 불가로 반증됨).
3. 시점 누수·전진 검증 필요는 v1과 동일 — **오늘 점수를 동결해 90일 뒤 대조, 첫 결과 2026년 11월.** k 그리드 판정(§10-4)도 여기서.
4. `market_orders` 셀러당 수집 캡(~900건)으로 분모 과소 — v1과 동일.
